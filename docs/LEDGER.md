# P0: журнал, счета, категории и переводы

Android 0.4.0 использует API после миграции `005_ledger_management.sql` и локальную Room 5. Сначала сделайте проверенную резервную копию PostgreSQL, примените совместимые миграции, затем обновите сервер и APK. Android сохраняет существующие счета, категории и операции при миграции локального кэша. Инструкции запуска находятся в [README](../README.md#quick-start).

## История операций

`GET /api/v1/transactions` возвращает `transactions` и `next_cursor` (строка либо `null`). Параметры: необязательный `account_id`, `limit` 1–100, `cursor`, `q` до 100 символов, `from` и `to` в RFC3339, `category_id`, `kind` (`income`/`expense`), `include_deleted`.

Начало периода включается, конец исключается. Android преобразует выбранные календарные дни из часового пояса устройства; конец периода — начало следующего дня. Порядок: время операции, время создания, UUID по убыванию. Курсор непрозрачен: передавайте его без изменений с тем же набором фильтров. Поиск выполняется по всей серверной истории. Новые записи и изменения во время просмотра могут поменять страницы — обновление начинает загрузку заново.

Офлайн доступна сохранённая первая страница конкретного фильтра, с явной пометкой об ограниченности данных. Кнопка продолжения работает при подключении. Приложение не скачивает всю историю автоматически.

## Изменение и удаление

Все новые изменяющие запросы требуют UUID в `Idempotency-Key`. Изменение, удаление и восстановление также требуют числовой `expected_version`. Сервер проверяет владельца, версию и ограничения в одной транзакции. При `409 version_conflict` обновите данные и повторите осознанное изменение с новой версией и новым ключом.

- `PUT /transactions/{id}` принимает полное новое состояние: `account_id`, `kind`, строку `amount_minor`, `note`, `occurred_at`, `category_id` (может быть `null`), `exclude_from_analytics`, `expected_version`.
- `DELETE /transactions/{id}` принимает JSON `{ "expected_version": 1 }`. Операция получает `deleted_at`, исключается из баланса и аналитики, но остаётся в истории удалённых.
- `POST /transactions/{id}/restore` принимает текущую версию удалённой записи и восстанавливает влияние на баланс.

У импортированных операций можно менять сумму, тип, дату, комментарий и категорию, сохраняя исходный счёт и связь с импортом. Отмена импорта удаляет и отредактированные, и мягко удалённые созданные им операции окончательно; последующее восстановление невозможно. Изменение отдельной части связанного перевода запрещено.

Перед отправкой Android сохраняет точное JSON-тело, пользователя и ключ в зашифрованном хранилище. При неизвестном результате повторяется исходный запрос. Старый ответ идемпотентности служит подтверждением запроса; актуальные значения загружаются отдельным GET. Приложение не вставляет старую версию записи обратно в кэш. Пока результат не разрешён, новые финансовые изменения блокируются, включая конкурирующий импорт.

## Управление счетами

`PUT /accounts/{id}` принимает `expected_version`, `name`, `type`, строку `opening_balance_minor`, `archived`, `include_in_balance`, `sort_order`. Тип: `card`, `cash`, `savings`, `credit` или `other`. Валюта созданного счёта неизменна. Изменение начального остатка пересчитывает баланс, не создавая доход.

Архивирование запрещает новые операции на счёт, сохраняя записи и отчёты. Архив и участие в общем балансе независимы: архивный счёт учитывается, если `include_in_balance=true`. История и аналитика не теряют записи при исключении счёта из общего баланса. Порядок задаётся целым `sort_order`.

## Управление категориями

`PUT /categories/{id}` принимает `expected_version`, `name`, `archived`, `sort_order`. Тип и родитель существующей категории неизменны. Новые подкатегории доступны только для расходов, в пределах одного уровня. Настройки стандартных категорий хранятся отдельно для каждого пользователя. Архив сохраняет назначения старых операций, но убирает категорию из выбора для новых.

`POST /categories/{id}/merge` принимает `expected_version` и `target_category_id`. Целевая категория должна быть активна и того же типа. Сервер переносит назначения всех операций исходной категории и её подкатегорий на цель и архивирует исходную ветку. Цель не может находиться внутри исходной ветки. Это действие требует подтверждения в интерфейсе; отдельной команды отмены объединения нет.

## Переводы между своими счетами

`POST /transfers` принимает:

```json
{
  "from_account_id": "UUID",
  "to_account_id": "UUID",
  "from_amount_minor": "5000000",
  "to_amount_minor": "10000",
  "fee_account_id": "UUID",
  "fee_amount_minor": "10000",
  "note": "Обмен тенге на доллары",
  "occurred_at": "2026-10-15T08:00:00Z"
}
```

Например, для счетов KZT → USD это списание 50 000 KZT, зачисление 100 USD и комиссия 100 KZT, если комиссия оплачена со счёта KZT. Минимальные единицы зависят от валюты, поэтому для JPY или KWD масштаб отличается. Без комиссии передавайте `fee_amount_minor="0"` и `fee_account_id=null`. Комиссию можно списать с одного из основных счетов или третьего своего активного счёта.

Для одинаковых валют две основные суммы должны совпадать. Для разных валют указывайте фактические банковские суммы: Frankfurter используется для справочной оценки портфеля, не для подмены условий перевода. Приложение записывает движение денег в учёт и не выполняет банковский платёж.

Перевод состоит из группы и двух связанных записей, плюс отдельного расхода комиссии. Группа сохраняется атомарно. Основные записи исключены из доходов и расходов; комиссия учитывается в расходах. Проверка переполнения балансов выполняется для всех затронутых счетов до завершения транзакции.

`GET /transfers/{id}` возвращает группу с частями; `GET /transfers` поддерживает курсорную загрузку. `PUT /transfers/{id}` принимает полный набор полей создания и `expected_version`. `DELETE /transfers/{id}` и `POST /transfers/{id}/restore` принимают версию и действуют на всю группу. Для восстановления все использованные счета должны быть активны.

## Проверка вручную

1. Создайте KZT-счёт с 100 000 KZT и USD-счёт с нулём. Запишите расход 1 000 KZT с прошлой датой; найдите его фильтром периода.
2. Измените сумму на 1 500 KZT, удалите и восстановите запись. После восстановления ожидайте 98 500 KZT; расходы — 1 500 KZT.
3. Запишите перевод 50 000 KZT → 100 USD с комиссией 100 KZT со счёта KZT. Остатки: 48 400 KZT и 100 USD; расходы KZT — 1 600 KZT.
4. Удалите перевод целиком: остатки возвращаются к 98 500 KZT и 0 USD. Восстановите — снова 48 400 KZT и 100 USD.
5. Переименуйте стандартную категорию в одном тестовом аккаунте и проверьте, что другой аккаунт сохранил стандартное имя. Объедините свою ветку категорий; проверьте старые назначения и отчёт.
6. Исключите USD-счёт из общего баланса, затем архивируйте его. История должна сохраниться, новые записи на архивный счёт недоступны. Верните счёт из архива и включите в итог.
7. Создайте больше 50 записей, проверьте продолжение журнала, поиск и фильтры. Отключите сеть, попробуйте сохранение и повтор после восстановления подключения: должна появиться одна операция. Для проверки реально неопределённого ответа используйте MockWebServer/instrumentation tests.

Серверные integration tests проверяют PostgreSQL и откат всей группы; Android tests — сериализацию, защищённое сохранение повторов и миграцию Room. Реальные банковские выписки в Git и публичные тесты не включаются.
